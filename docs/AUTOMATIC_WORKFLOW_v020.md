# 移行パッケージの作成・復元・再開（v020）

登録済み Study 38 / Gait120 の処理について、URL取得から判定までの実行に加え、
移行用パッケージの作成と移動先での再構築を実装した。対象はこの2研究であり、
任意の研究や振幅の研究間統合へ適用範囲を広げたものではない。

## 今回作成した保存物

- データパッケージ：`paper/results/timing_transfer_v001_2026.09.14-r1.zip`
  （1,486,791,981 bytes、約1.49 GB）。原データ11ファイル、文献、固定プロトコル、
  20組の照合用曲線、由来情報の34ファイルと、相対パスのハッシュ一覧を収録。
- 固定実装：`paper/results/timing_transfer_software_v001_2026.09.14-r1/implementation.bundle`
  （Git commit `3e94f318d248ce15638086696d5dd83c0a97e36e`）。
- 導入用wheel：同じフォルダの `harmo-0.3.0-py3-none-any.whl`。
  開発版の保存物であり、PyPIへの新規リリースではない。
- 復元結果：`paper/results/timing_transfer_restore_v002_2026.09.14-r2.json`。

データパッケージの SHA-256：
`22882c9be6cfc102289b3d80e4c0180a70a3d0111e0f9abfd091f9191da259f3`

## 1. 移動先への導入

データZIPと固定実装bundleを移動先へコピーする。公開ゲートのコード由来を保持するため、
固定実装のクローンから実行する方法を推奨する。Python 3.12で検証した。

```sh
git clone implementation.bundle harmo-transfer
cd harmo-transfer
python3 -m venv .venv
. .venv/bin/activate
python -m pip install ".[timing]"
```

bundleのクローンは固定コミットのdetached HEADになるが、この実行用途では問題ない。
導入時のPython依存パッケージは別途必要であり、データZIPに実行環境や実行コードは
含めていない。依存関係を事前に導入すれば、以下の復元には通信を使用しない。
wheelも用意したが、wheel単独の導入だけではクリーンなGit由来を保証しないため、
既存の公開ゲートが保留することがある。そのゲートは緩和していない。

## 2. 復元

クローンしたクリーンな実装ディレクトリ内から、次を実行する。

```sh
harmo timing-package restore \
  --package /absolute/path/to/timing_transfer_v001_2026.09.14-r1.zip \
  --output /absolute/path/to/NEW_RESTORED_DIRECTORY
```

このコマンドは、元のカタログや実行履歴の絶対パスを書き換えない。
パッケージから原データ・文献・条件を検証して取り出し、新しいパスでカタログ、
100処理計画、生理学的検証、20組の比較と公開判定を作り直す。
最後にパッケージ内の照合用曲線と全点を比較する。以前の公開許可は引き継がない。

- 終了コード0：復元、20組の公開判定、参照曲線との完全一致が成立。
- 終了コード2：公開保留または参照曲線との不一致。詳細は結果JSONを確認する。
- 終了コード1：捕捉した入力検証・実行エラー。

`restore.status.json` に段階と状態、`restore.result.json` に照合結果を保存する。
実データと契約は `workflow/` 以下に生成する。過去の参照曲線は再現確認の対象であり、
科学的妥当性や公開許可の代用にはしない。

## 3. 途中再開

同じコマンドに `--resume` を追加する。パッケージの同一性、展開済みファイル、
マッピング、カタログ、処理結果を確認して再利用する。失敗した段階は別の試行フォルダに
再実行し、失敗結果は残す。個々の周期内ではなく段階単位の再開である。

復元済みフォルダを後で移動する場合も、内部パスを置換するのではなく、元のZIPから
新しい場所へ再度復元する。実装や入力が変わった場合は別の出力先を使用する。

## パッケージを新たに作成する場合

```sh
harmo timing-package create \
  --workflow /absolute/path/to/completed-planned-url-workflow \
  --source-cache /absolute/path/to/registered-sources \
  --protocol /absolute/path/to/physiology_positive_control_protocol.yaml \
  --article /absolute/path/to/registered-study38-article.xml \
  --output /absolute/path/to/NEW_TRANSFER.zip
```

`harmonize --timing-profile study38-gait120-planned` で完了したワークフローを指定する。
元の段階別成果物と公開対象の処理履歴を再検証してから収録する。既存ZIPは上書きしない。
作成途中の失敗で不完全なZIPが残る場合があるが、復元前の整合性検査で拒否される。
共有時は元データの利用条件も維持すること。

## 安全性と検証結果

- ZIPのパス逸脱、重複、リンク、未登録ファイル、暗号化、容量超過、ハッシュ不一致を拒否。
- 入れ子の参照NPZにも展開容量制限を設け、有限の101点配列・位相軸を確認。
- 自己整合したハッシュ一覧だけでは許可しない。固定プロトコル・文献ハッシュに加え、
  登録済み原データのサイズとMD5を再検証する。一覧は電子署名ではない。
- 最終実装で関連テスト53件が通過：`paper/results/timing_package_tests_v003_2026.09.14-r3.xml`。
- 元プロジェクト全体の読み取りと通信をOSサンドボックスで禁止し、別パスから復元。
  両方の禁止が有効であることも試験した。
- 1,211件のカタログを再生成し、100処理計画、新規の生理学的検証、20組の公開判定が成立。
  40曲線・4,040点と位相軸が移動前の参照値と完全一致した。
- その後の再開では、新規登録0件、1,211件再利用、入力・マッピング・処理段階を再利用した。
- wheelの生成・依存関係を省略したインストール・CLIヘルプとスキーマ配置を確認。
  wheel内のPythonファイル157件が固定実装と一致。実データ復元は既存の依存関係が揃った
  実行環境で確認した。空の環境への依存関係一括導入は今回の実データ検証に含めていない。

これは同じMac上での隔離・別パス復元の実証であり、別の物理PCや別OSでの数値一致の
実証ではない。実装・依存関係・計算環境の差がある移動先では、実際の再検証結果を採用し、
不一致や保留を自動的に解除しない。

元の作業リポジトリはコミット／プッシュしていない。固定実装のコミットは隔離した
検証用リポジトリに限る。論文本文と固定プロトコルも変更していない。
